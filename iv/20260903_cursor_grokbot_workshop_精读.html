Grok Bot 工作坊实录：录屏就能教出一项技能、权限用自然语言逐条设定、五个工程人格靠 API 契约接力（Cursor 产品工作坊，2026-09-03）

Cursor 官方频道 · 产品工作坊 · 65 分钟 · 2026-09-03

这是 Cursor 官方频道的产品工作坊，与同一产品的那期访谈分工不同：访谈讲的是产品怎么被做出来，这场讲的是机制与用例，因此本文只取工作坊独有的部分。值得读的原因有三：它把记忆、技能、例程、权限四套机制逐个点开，并暴露了各自的边界；它给了一个工程场景的完整接力演示，五个按角色定义的代理靠 API 契约协作；问答环节有一位客户给出向 130 人铺开的真实前置条件，这是应用层采用成本的直接读数。

口径提示：产品名在自动字幕里有 Grockbot、Grockpot 等多种拼写变体，本文统一写作 Grok Bot；演示者姓名按字幕还原，识别不清处写作演示者。全片无收入、留存与定价数字，唯一的商业口径是订阅门槛。

一、产品定义与心智模型的转向

演示者给的定义是一支常开的代理团队，三条支柱是每个 bot 有记忆、能拿到工具、有自己的电脑。她把主旨表述为一次心智模型的转向：“我们此前处在一个多数时候只是要求代理替我们做事的世界。我们正在从基于任务的心智模型走向基于角色的心智模型。”

界面被刻意做成消息应用的样子，理由是“你会像和朋友、和同事那样跟这些代理共事”。可以像在群里 @ 一个人那样 @ 某个代理，代理之间也会互相讨论，她笑说“它们有时候彼此之间会相当呛”。个人场景的编制是一个 chief of staff 带收件箱管理、日历排程与待办整理三个工具型 bot。演示中也能看到摩擦：语音转写的待办需要手工改，两个 bot 此前被删导致其他代理临时改了协作对象。

二、工具接入的边界，兜底靠在虚拟机上点像素

工具走单一插件入口加授权，已连的有邮箱、云盘与日历，可连的包括 Notion、Slack、Salesforce、Clay、HubSpot、GitHub、GitLab、Datadog 等。一个实用细节是可以同时接个人邮箱、与伴侣共享的日历、工作邮箱，它能分辨不同账号。

边界在现场暴露得很清楚。PowerPoint 不在插件里，自定义的事故管理工具需要回到 Cursor 去配一个协议服务，她把这件事明确列为你可能还需要 Cursor 的一个理由。兜底路径是在 Linux 虚拟机上直接打开 PowerPoint，教你的 chief of staff 怎么做幻灯片，代价是一次人工录屏。

三、技能与例程：录屏教学是这场演示里最有信息量的机制

技能是名称、描述、指令的三段式结构，可以发布共享。真正值得记的是教学方式：她说有时更愿意亲自教它一件事怎么做，于是现场录了一段订机票的操作，把这段演示直接变成一项技能。同一手法也用来把“深夜洗衣服”存成技能。

例程是把工作流固化下来，演示的是早间简报，翻收件箱、汇总新闻信、发一条 Slack 消息。触发器分两类，可以是时间型的，也可以由一条消息被发出触发、或由一次事故被启动而触发。她提到有人用电脑使用加例程来报销，不必再手工做。整场关于收益的表述只到省时间，没有任何量化。

需要留意两处（作者归纳）：技能在这里是显式暴露给用户的对象，与那期访谈里“抹掉高级用户抽象”的说法存在张力；共享技能缺治理机制，版本、回滚与权限都没有交代。

四、记忆与权限：一处技术口径，一处未解张力

记忆机制她说得很直接，Grok Bot 的记忆存在对象存储里，因此没有上下文窗口上限，不必担心上下文退化。问答里她承认两点限制：冷启动问题大概都会在，新代理仍需手把手；目前的记忆更接近照相式的记忆，改进记忆被称作第一号特性。界面上没有记忆浏览或编辑入口，组织级记忆未演示。

权限有三层。可以要求逐动作审批，也可以用自然语言给出粒度很细的规则，比如发给外部供应商的邮件先问一次、写共享日历先问一次。第一次使用时它会主动问你，要我做这个吗，要我以后总是这么做吗，还是永远不要这么做。演示里出现了三次实时审批与一个仅此一次允许的档位。她有一句话把这套设计的来源讲清了：“它在自己发明例程，所以它来问我这样行不行。”

这里有一处未解的张力：产品定位是常开且自主，而审批必然把流程挂起等人（作者归纳）。

五、工程场景：五个人格靠 API 契约接力

这是全场唯一有明确交付物与验收标准的演示。五个按角色定义的代理跑一个住宿预订特性，后端定 API 契约、前端等契约、另一个代理等两侧的合并请求。她强调这些代理按角色定义，所以后端那个并不只能在这一个仓库里干活。协作的价值她概括为“这基本上把你本来需要的那些空转的会议时间省掉了”。

质检那一环给出了可验证的形态：代理在自己电脑上跑本地端口、录端到端视频、用网络面板的截图确认后端也在工作，然后贴进合并请求。另有两个常驻代理，一个看守持续集成、判据是测试是否全绿、不绿就自动重试，一个值班代理每 15 分钟轮询监控系统，触发条件是接口错误出现尖峰或面向客户的事故在烧。

与自家编码产品的分界她划得很清楚：这件事更多关于编排你的代理，实现层仍然留给 Cursor 那一侧。

六、规模、定价与一份真实的铺开清单

数量上限她给的是五六个代理大概就是她希望同时互相对话的上限，另一位演示者日常跑十二到十五个。主持人形容使用者的角色是“你在这里当 CEO”。她认为语音模式是在路上使用这个产品的关键，每个 bot 有自己的人格与声音，可以加入群通话。

商业口径只有一条：访问权来自 Cursor Ultra 账户或 Super Grok Heavy 账户，全场没有按用量或按成果计价的表述。

问答里一位客户给的铺开条件值得单独记下：计划推给 130 人，在铺开之前先招了一位 AI 与商业智能方向的资深总监和一位自动化工程师，把部落知识的文档化列为头号障碍，并要求被动的工作流发现能力。答复是当前只能靠录屏教学加喂文档，因为“你给的上下文与信息越多，它做判断或者做事就越好”。

与《应用是如何诞生的？》的对应关系（作者归纳）

报告把编码归为已具备替代性，理由是测试可自动判定、用户具备技术背景、上下文集中在代码库，这场工程演示是这三条的逐条照映：产出以合并请求交付，正确性由单元测试加端到端录屏判定，使用者能读代码差异，上下文集中在一个仓库里。看守持续集成的代理更彻底，判据就是测试是否全绿。

报告说企业代理尚不具备替代性，这场工作坊整体构成支持，而且支持的方式是把成本显性化了。跨系统这一条，现场点到的工具接近二十个，与报告说的横跨约 20 个系统量级吻合，而插件覆盖不全时要退回点像素。面向非技术用户这一条，证据是这场工作坊本身就是采用成本的一部分，团队还在按职能排后续场次，而那位客户在铺开前先招了两名技术岗。

反例只在两处：有自动判据的编码与编码相邻工作流，以及判据能写成阈值的运维监控，比如按接口错误尖峰触发的值班代理。个人事务类工作流跑通了流程却没有验证机制，验证方式就是演示者自己打开日历一条条看，不过这些任务的失败代价都很小。

报告说的任务全成本，产品的处理办法是把它挪出价目表：重试塞进看守代理的自动循环，人工复核压成一次点击审批，失败风险变成一条自然语言规则，成本因此落到订阅费与用户注意力上。还有一条报告的框架需要修正：Grok Bot 与模型同属一家，这种纵向整合抹掉了报告假设的模型层与应用层界线。
