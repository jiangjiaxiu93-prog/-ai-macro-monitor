NVIDIA 讲 tokenomics：token 是基建投资与 ROI 之间唯一的桥，而并非所有 token 等价，用例决定你该买哪一种（AI Factory Insider Ep.4，2026-09-01）

NVIDIA · AI Factory Insider Ep.4 · 34 分钟 · 2026-09-01

本期是 NVIDIA 自家 AI Factory Insider 系列第四集，主持人 Kaushik Shirhatti（AI 工厂业务副总裁）对谈 Shruti Koparkar（AI 基础设施产品市场高级经理，刚与人合著了一份 tokenomics 白皮书）与 Tue Tran（GTM 战略运营，在做 tokenomics 的内部测算工具）。这期值得读的原因有三：它是厂商侧目前把"每个 token 的成本、需求、价值"讲得最结构化的一次公开材料，给出了需求估算的三层法与供给侧的三层效率分解；它提出了一个对应用层定价有直接含义的框架，即 token 的价值由嵌入的智能、可看的上下文与到达速度共同决定，因此为不需要的场景买旗舰 token 是纯粹的浪费；它给了一个可被引用的采纳侧数字，某电信客户发现开发者习惯默认调用旗舰模型，但实际只有 8% 到 16% 的任务真的需要。需要提醒的是，这是厂商自制内容，落点始终是自家产品（NeMo Switchyard、NeMo Relay、Dynamo、NVL72、Nemotron），框架可用但结论带立场，其中的比例与案例均为口播且未给出处。

一、为什么用 token 记账：客户不关心工厂内部，只关心第一个 token 何时落地

开场把记账口径立住。主持人说，如果你在为公司建 AI 工厂，要始终记住你的客户，而"你唯一的客户就是那些用户、机器和智能体"，他们会借 AI 的力量让公司、公司的产品与服务变好。关键的一句是这些客户"不关心工厂里面发生了什么，不关心工厂怎么建的、用了什么基础设施、用了什么软件。他们唯一关心的是业务成果何时落地，而那发生在第一个 token 落地的时候"。

由此得出这期的方法论前提："如果你想把基础设施与 AI 工厂的投资，和业务上的投资回报率挂上钩，那座桥就是产出，而产出就是 token。"这句话是全集的骨架，后面的需求、供给、变现三段都挂在它上面。这个记账方式本身值得注意，它把一笔资本开支的回报问题，转换成了一个单位产出的价差问题，与卖方研究里用单位经济性替代总量叙事的做法是同一路数。

二、token 与 tokenomics 的定义：价差决定一个用例能否活过试点期

Koparkar 给 token 的定义是"人工智能最基本、最基础的单位"。对语言模型，它是"一组数字，通常代表四个字符"，再简化可以理解为代表一个词；对图像生成模型，最基础的单位是像素，token 是代表一个像素的一组数字；对生物学模型，可能是代表蛋白质分子结构的东西。她的收束是所有 AI 回答、所有智能体做的活，最终都建立在这些 token 上。

Tran 说 tokenomics 这个词还没进词典，但"照这个势头，它可能会成为 2026 年的年度词汇"。定义不意外，就是 token 与 economics 的合成，指的是对生成一个 token 的经济学的审视："生成一个 token 的成本是多少？这些 token 的需求是多少？让这些 token 被生成出来的价值是多少？"他给出的落点是价差：价值与成本之间的那个差额，是企业真正在意的东西，而"它真正决定了一个 AI 用例是被规模化、在公司里取得成功，还是在试点阶段之后就被砍掉"。

这是全篇最有转述价值的一句。它把 AI 项目的生死判据从"模型好不好"移到了"单位价差正不正"，也解释了为什么大量企业 AI 试点无法进入生产：不是技术不成立，而是在那个特定用例上，token 的价值撑不起生成它的成本。

三、并非所有 token 等价：智能、上下文、速度三个绝对维度，加一个相对维度

被问到怎么给 token 分桶时，Koparkar 用了大宗商品的类比：我们确实把 token 当商品谈，但"即便是商品，比如一袋米，也分不同品种，有白米、茉莉香米、糙米，品质各不相同。token 也一样，并非所有 token 生而平等"。

她给的价值构成有三条。第一是嵌入其中的智能，取决于生成它的模型，模型更复杂更智能，token 就带更多智能。第二是上下文，即模型能同时看多少数据，允许模型看更大的上下文，它产出的 token 就更智能。第三是到达速度，即 token 的生成速率，也就是她所说的交互性（interactivity）。

关键的补充是这三条是绝对视角，还存在一个相对视角，即"你的用例需要多少 token 价值"。她的判断很直接："如果你在不需要溢价 token 的用例上使用溢价 token，那么溢价 token 提供的所有额外价值都被浪费了，这对经济性显然是坏事。"由此得出这期最核心的操作概念，token 效用（token utility）：把用例映射到正确的 token 价值与 token 效用上。主持人用一句玩笑把它落地：同一个周末，有人用同样数量的 token 做了了不起的研究，而他在生成猫的视频，"做研究也许该用溢价 token，而如果你只是生成猫视频，你不需要为溢价模型付钱"。

四、场景匹配的两组例子：交易台的两种速度，与零售的一个 token 对一百个 token

Tran 只取智能与速度两个轴，给了两组行业例子，这是全篇最实用的部分。

第一组是金融服务与资本市场客户，他们的交易或投资活动有三种不同速度。极高频那一端，速度就是一切，必须有极低时延，但他的观察是"在那个速度上，他们需要做的决策其实相当简单"，所以真正要最大化的是生成这些简单 token 的速度。另一端是做五年或十年投资论文的人，论文以周或月为单位形成，"一份好报告对这样成熟的投资者来说是个好起点，他们可以等两小时，可以等一小时"。他们真正在意的是这个 token 被一个非常好的模型带着大量上下文反复推理过，几百份不同的报告被塞进去，"有子智能体在互相积极地反驳，真正确保论证是站得住的"。在这个场景里速度的重要性低得多，准确度与智能高得多。

第二组是零售。一个是监控摄像头，引用了 NVIDIA Metropolis 团队的蓝图，模型只是盯着流媒体视频，给一个 token 的答案，有没有事件发生，比如有没有偷窃，"就那一瞬间，它只需要给你一个非常短的答案，是或否"，然后一遍遍地看下一段视频。另一个是同一家零售连锁给客户寄来的视频或广告视频做字幕，同样是十秒的片段，模型要生成一百个、两百个 token，"但他们不必实时做，可以放到晚上批处理"。同样的素材，token 的量与质高得多，速度要求低得多。

这组对照的意义超出了 NVIDIA 想讲的产品。它实际上说明 token 消耗量本身不是有效的需求指标，同样的业务动作可以对应差着两个数量级的 token 账单，取决于产品形态是实时判定还是离线生成。任何用 token 总量推算收入或算力需求的做法，都要先问清楚是哪一种。

五、需求怎么估：三层法，以及会让需求爆炸的几个乘数

回答观众关于"如何为重要项目估算 token 数量"的提问时，Koparkar 给了一个分层方法。

第一层是"背包算术"（back of napkin math）：你有多少用户，他们在你的分析周期内会发起多少请求或会话，以及每个请求需要多少 token。最后这一项取决于用例，聊天类用例需要的 token 少于智能体类用例。三个数字相乘得到基础需求。

第二层是几个"很关键、可以让 token 需求迅速爆炸"的乘数。其一是是否使用推理模型，因为"推理模型会生成用户看不见的思考 token，但你仍然得把它们生成出来"。其二是是否为智能体工作流，主智能体会派生多个子智能体与工具调用，走一遍规划、行动、再规划、再行动的循环直到拿到结果，这些循环都推高需求。其三是缓存命中率，方向相反，如果语言模型见过同样的提示词，有时不需要重新计算和处理，可以直接取用已处理的 token，这会压低需求。

第三层是运营因素：负载在一天中如何变化，早高峰夜低谷，以及季节性，零售客户在节日推产品时对 token 的需求会大增。她承认"听起来复杂，但一旦开始动手做，一切其实都回到用例"。

被追问缓存命中率是否指 KV cache 时，她确认并补充说明。KV cache 简单说是模型的短期记忆，模型处理输入提示词时会算出对应的 KV 值并存下来，因为生成后续输出需要它们；后面进来的提示词如果与之匹配，就可以直接取用。相关的还有提示词缓存与前缀匹配，即把进来的输入与已见过的部分做匹配，让系统聪明地避免重复计算。她举的高命中率场景是企业内部搜索，因为"很多人都在问，我的 401(k) 信息在哪儿找？我的工资单在哪儿找？"，提示词高度相似。

六、供给侧：AI 工厂像发动机，效率分模型、硬件、软件三层

Tran 用汽车发动机类比供给侧：能量进去，东西出来，发动机看马力，AI 工厂看吞吐，即每台发动机、每座工厂每秒能为你生成多少 token。他把决定生成速率的因素归为三类效率。

模型层的效率变化他讲得最细。早期大语言模型参数较少，但属于稠密模型，"每次你想生成一个新 token，都必须读取并对每一个参数做数学运算，那是大量的运算"，而参数量又与智能相关，于是权衡近乎"你得不到多少智能，却还是得做大量运算"。更现代的架构是混合专家（MoE），参数可以多得多、训进去的知识多得多，但每次生成新 token 只读取所谓相关的专家，"于是你做的运算少得多，得到的答案反而更好"。代价在网络：MoE 的专家可能分布在不同 GPU 上，为了让 token 被正确高效地生成，GPU 必须在那些瞬息之间不断互相通信，所以网络必须非常好。

硬件层的效率就是上面那件事的延伸。软件层他强调必须以正确方式与硬件对话，并有效编排调度任务运行的时机，让停机尽可能少、整个集群的利用率尽可能高。三层叠起来，才构成一座能把投入的能量转成 token 的完整 AI 工厂。

七、选对模型比选对硬件更早决定经济性：只有 8% 到 16% 的任务需要旗舰模型

Koparkar 接过来把供给侧收到两个选择上：你选什么 token，以及你选什么基础设施来生成它们。而选什么 token 又回到选什么模型，"对你的用例来说，不是每个用例都需要溢价模型"。

她给的案例是全篇最有引用价值的数字：某电信客户发现，尽管"很多开发者总是默认用溢价模型，实际上只有大约 8% 到 16% 的任务真的需要溢价模型"。其余任务他们本来就可以、现在也确实已经转向使用经过后训练的开放模型，或者在某些情况下通过 API 消费一个更小、更贴题的模型的 token。

做到"对的任务配对的模型"靠智能路由，她借此引出 NeMo Switchyard，NVIDIA 作为 NeMo Agent 工具包一部分新发布的东西，可以基于模型匹配度、定价、成本画像等因素把进来的请求路由到合适的模型。第二件事是可观测性，企业需要知道 token 去了哪里、什么 token 被用在什么用例上、是否真的产生了业务价值，对应产品是 NeMo Relay，她强调这些都是开源软件。基础设施侧，NVL72 系统适合 MoE 模型，但企业并非总是从白纸开始，所以还有 HGX 系统直到 RTX PRO 服务器等不同规格来匹配现有环境与能耗约束。软件侧她引黄仁勋的说法，Dynamo 是 AI 工厂的操作系统，负责调度、把请求发给正确的 GPU、让工厂始终保持高利用率。主持人的收尾是这就是他们称之为"极致协同设计"的原因，横跨计算、存储、网络、软件、安全。

这一段的产品营销成分最重，但剥掉产品名之后剩下的判断是成立的，并且对应用层公司有直接含义：模型选择与路由发生在硬件选择之前，且对单位成本的影响可能比换硬件更大。8% 到 16% 这个区间如果在别处能被复现，意味着当前旗舰模型的调用里存在大比例的过度供给。

八、变现的四条路径与 ROI

被问到变现，两人合起来给了四类。第一是直接卖 token，把生成的 token 供给市场让人来买，"几乎就是云的模式"。第二是靠只有你才有的智能产生直接收入，Tran 把它与提供服务区分开。第三是 AI 原生产品，即用 AI 建起来的产品，Koparkar 说的"我们看到的所有这些新一代公司"，以及把 AI 注入现有产品让产品更好或提供差异化能力。第四是用 AI 改造内部运营，不以对外产品的形式出现，可能是提升员工生产率，也可能是优化供应链管理。

主持人在最后一类上加了一句："AI 给了每个人的机会，不只是在内部优化一个流程，而是重新想象这个流程。"Tran 关于工具的说法值得一记：一两年前他会回家打开 Excel 建模型，"就这么简单"，而每个企业、每位 CFO、CEO、COO 今天都能做这件事；现在借 AI 工具本身可以更有效地把业务逻辑做进工具里。他给所有还在观望 tokenomics 的组织的唯一建议是"就是开始做"，因为虽然因素很多、兔子洞可以无限深，但起步时的驱动变量相当清晰简单，从高层次开始、边做边细化、并且要让业务侧和 IT 侧一起参与，业务侧定义用例与所需的速度和质量，IT 侧回答什么是对的发动机、上云还是本地。

九、token 海啸的护栏：不是压需求，而是让每个 token 的 ROI 站得住

观众问该用什么护栏来限制"token 海啸"。Koparkar 提到她曾与机场 AI 联盟的一群 CEO 讨论过是否该给用 AI 的人设 token 限额，她说自己并不必然反对，但给出的框架是另一个方向："token 海啸之所以成为海啸，只是因为你没看到成果。如果你的 token 需求很大而你也看到了对等的成果和 ROI，你会很高兴。"

所以她的处方仍然是从用例出发，弄清需要什么 token 效用，再去想供给侧如何最大化，选基础设施也选对的模型。她举的例子是能否使用更高效、在智能体上走更高效轨迹的模型，"比如 Nemotron 3 Ultra 每轮用的 token 更少、总轮数也更少，这样为了同样的成果，它需要的 token 就更少"。推导是把每项任务的 token 数降下来、把每个 token 的成本降下来，就降低了每项任务的成本，ROI 就开始显现。她的结论句是"这与其说是要最小化 token 需求，不如说是要确保你认为自己需要的那些 token 的 ROI 是合适的"。主持人补了一句方向性判断：如果前期功课做足了，你不会想去压制真正驱动创新的东西，"token 是创新的燃料"。

十、企业侧的落点：AI 工厂可以从 16 到 32 张 GPU 起步

收尾时主持人做了总结，并强调了一个他说自己每周都在纠正的误解：人们一想到 AI 工厂就想到吉瓦级的庞然大物，行业里确实有巨大的基建扩张，云厂商在建，但那些是全新场地。"而对企业来说，它可以从 16 张 GPU 开始，可以从 32 张 GPU 开始，你可以爬、走、再跑。"路径是先做几个用例、理解那些负载、给项目排优先级，然后开始学习和微调，再把 AI 工厂规模化。

这个落点与全篇的记账方式是自洽的：既然判据是单位价差而不是总量，那么起点规模就不必大，先把某一个用例的 token 效用、需求与供给算清楚，再复制到下一个。
