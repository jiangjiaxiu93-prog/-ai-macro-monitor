xAI 团队 72 小时直播建公司：产出一款靠直播流量的网页卡牌游戏、约 274 个 PR、零收入；客服场给出每张工单 1 到 2 美元、批处理 0.2 美元的单位成本，编码执行层多处明言“底下是 Cursor”（Grok Bot Galaxy 三日直播，2026-09-22）

Grok Bot Galaxy 直播三日精简版（Chansoo Byeon 频道转载），3 × 240 分钟 · 2026-09-22

本文合读的是 xAI 在旧金山 Dreamforce 会场旁举办的 Grok Galaxy 活动期间、三位员工（开发者体验 Matt Palmer、产品 Roshan、做 Grok Bot 的 Lauren，网名 Potato）连播三天“用 Grok Bot 在 72 小时内建一家公司”的精简版，中间穿插了 xAI 与 Cursor 员工面向工程、产品、销售工程、销售、SDR、客服、收入运营、售后、营销的九场主舞台演讲，以及 Peter Yang、Codie Sanchez、Karen Cheng 等外部嘉宾连线。口径提示放在前面：这是一场产品推广直播，三天里五次口播 Starbase 观看星舰发射的抽奖、三轮“价值 200 美元的最高档免费月”赠送，所有用户数、直播在线数、内部效率数字均为讲者口述，无独立核实；自动字幕把 Grok Bot 记成十余种拼法、把 xAI 记作 SpaceX AI、把疑似 Cursor 的公司名记作 Kurt，均按上下文还原，拿不准处在文中注明。本文只取投研相关线索：产品形态与竞争定位、编排层与执行层的分工、定价与单位经济、企业采用路径与护栏、官方承认的短板，以及这场 72 小时实验本身的含金量。中心判断是：Grok Bot 把“多 bot 团队、每个 bot 一台云端电脑、计算机使用兜底、模板市场”四件套做成了平台自带能力，讲者反复强调“没有 MCP 不是阻碍”，而全场唯一给出的单位经济数字来自客服场景，量级与按解决量计费的第三方客服 agent 处在同一区间（作者归纳）。

产品形态：iMessage 式的 bot 团队，每个 bot 一台云端 Linux 虚拟机，记忆存 S3，密钥不出客户端

售后场讲者 Blake 开场就说“看着像 iMessage，我们确实抄了 iMessage”。左栏是一组有固定职责、长期保留的 bot，101 场的 Roman 把设计决定归为三条：按工作单元建 bot、与按任务开新聊天相对，bot 会记住几周前说过的格式偏好；每个 bot 有自己的电脑，除了 MCP 与 API 还能像人一样看视频、听播客、点老旧的政府网站，他说区别在于“做到九成”与“端到端做完”；全部跑在云端，批评现有 AI 工作流绑在本地笔记本上，凌晨两点的定时任务会因为合盖不触发。营销场的 Josh Kim 把这条说得更直白：“不用再开着笔记本或配一台 Mac mini”，这是对本地常驻 agent 方案的隐性比较，工程场的 Lingxi 则直接点名，说自己曾是 OpenClaw 等本地 agent 的重度用户，“它们做不好工程，因为缺一方集成”。

技术细节由 Q&A 给出：bot 的电脑是轻量 Linux 虚拟机，一个账号下的多个 bot 共用一台虚拟机的文件系统但各有独立记忆；记忆存在 Grok Bot 内的 S3 桶里，可口头让它忘掉；1Password 一类的密钥在客户端弹安全模态框录入，“不暴露给 xAI 一侧”，bot 看不到密码；把 bot 分享为模板时带走记忆、指令与一方插件，不带聊天记录与敏感数据。截至 Day 3，客户端覆盖 iOS、iPad、Android、Windows、Linux、macOS，语音模式在 Day 3 当天宣布上线并数日内推送。Day 3 时 Roshan 展示的插件列表有 Slack、Vercel、X、PlanetScale、Notion、Clerk、Excalidraw、Remotion、1Password，即将上线 AgentMail、Canva、Clay，任意 MCP URL 可直接安装。Lauren 的判断是“Grok Bot 最重要的事甚至不是建 bot，是把你所有的工具和插件接上”。

编排层与执行层分工：Grok Bot 是轻量 harness，代码交给 Cursor cloud agents

三天里最一致的表述是分工。Day 1 Matt 解释：“Grok 是模型，然后有 harness……Grok Bot 很轻量……正经的工程工作我们会踢给 Cursor，Cursor 的 harness 很擅长写代码。”销售工程场的技术专家 bot Sherlock“底下用的是 Cursor cloud agents”，营销场的 website ops bot“底下是 Cursor”，Day 3 修 bug 的口令是“用 Cursor cloud agent 去调查，先别开 PR”。Lauren 的工作流是在 Grok Bot 里口述、用 Cursor 的插件与自动化写码与审 PR，她说“Cursor 更像编码工具，Grok Bot 做知识工作的通用 bot，两者配合很好”。

讲者对两家公司的关系有多处直接表述，字幕原话如下，本文未做外部核实：Lingxi 自述“我加入了 Cursor，现在是 xAI 了，不到九个月已经发了两个产品”，此前做 Cursor 3 的 agent 窗口，现在做 Grok Bot；创始人场的 Shub 说与 Cursor cloud agents 的一等公民集成“算是 Grok 与 Cursor 在一起的福利”；Day 2 主持全部工作坊的讲者自称“Cursor 的现场工程师”，其客户案例幻灯片全是“某公司如何使用 Cursor”；Matt 说自己入职“正赶上这次收购”；客服场答定价时说用量计入“你的 Grok 订阅或目前的 Cursor 订阅”。Lingxi 给出的团队效率口径是 Cursor cloud agents 的 automations 让“Cursor 团队几乎每个人都 10 倍了”，他一人三周做出 Grok Bot 移动端首版，管理 15 个 cloud agent 时已经吃力，Grok Bot 的用途之一就是替他写提示词、排队与催促这些 agent。

定价与单位经济：不单独收费，最高档月约 200 美元，客服每张工单 1 到 2 美元

Grok Bot 没有独立价目表。客服场被问定价时的回答是“用你通过任何 Grok 订阅或目前 Cursor 订阅拥有的用量，它只是跟踪用量”。三轮赠送都以同一口径计：“一个月免费，价值 200 美元，我们的最高档位”，Day 3 又提到给排行榜前十送“Grok Bot Ultra plans”需内部审批，可推断最高档月费约 200 美元（促销口径，作者归纳）。Day 2 的赠送名额首次口播“前 1000 名”，第二次改为“前 10000 名”，原样记录。

唯一的单位经济数字来自客服场的 David。他说按自己目前的用法，“回答中到高复杂度的工单大约每张 1 到 2 美元”，对低复杂度的计费类工单先用脚本分桶再批量回复，“可以压到每张 0.2 美元左右”，对比对象是“其他客服 agent 通常按解决量收费，至少 1 美元，一般在 1 到 10 美元之间”，人工更高。他补充这只是“花了半天调优”的结果，并演示让 bot 在 Postgres 里自建 eval 表与 trace 表记录每次回复看了哪些文件。SDR 场被问“每天 50 条线索要花多少 token”时，回答是“很难说，取决于拉多少 Gong 通话与 Databricks 上下文”，建议改成每周一次 250 条，没有美元数字。

成本控制话术贯穿三场 GTM 演讲：少跑例程，曾有人误设每 15 分钟一次；直接用专才 bot、少让 chief of staff 编排，省 token；“有 MCP 就别用计算机使用”，Gong、Granola、Salesforce 等已开箱提供；别滥建 bot，SDR 讲者说“我一度有太多 bot，反而更乱”；模糊指令如“回复 Alex”会让 bot 拉全部工单做字符串搜索，直接给工单号便宜得多。创始人场的 Shub 对多 bot 群聊的提醒是“它们会互相抢话，而且随着做的事越来越多会变得很贵”，建议少用群聊、按需 @。销售场的 Mark 则给出成本叙事的另一半：“我们用一方模型，这确实有助于降低成本。”

企业采用路径与护栏：自下而上起步、角色模板分发、系统记录之上的编排层

销售场对企业标准化部署的描述是三段：起点是“每个人装上 Grok Bot、先为自己建”；正在推的变化是登录时询问角色并预置模板；较先进的公司由 power user 建模板向团队分发，“作为销售代表，我登进来就有这五个 bot”。Christa 把 Grok Bot 定位为“所有这些工具之上的编排层”，数据可能在 Databricks、Salesforce、Notion、Slack 任何一处，Salesforce 仍是 source of truth。这是一种坐在系统记录厂商之上、以“没有 API 就登录网页”绕过集成缺口的定位（作者归纳）。

护栏方面各场口径一致：先只读，再开写权限并要求人工审批，不同 bot 权限分开；企业管理员可限制 bot 访问的网站与下载；关键动作弹出审批，已授权动作可改“always allow”；营销场提到有数据隐私模式可选择是否用于训练，安全问题“逐案处理”。Josh Kim 说“xAI 有工程师带着整队 bot 直接把代码推到生产”。

比示范项目更值得引用的是 xAI 员工对内部效率的自述：收入运营讲者的“给线索用的约会应用”（AE 左滑结束线索回写 CRM、右滑进跟进序列）“从想法到落地两周，实际构建时间约 10 小时”，其余时间用于培训销售；售后讲者说自己九到五里 75% 是会议，一个 Scout bot 替代了过去 30 到 40 个 Slack 频道，他只与一个 chief of staff 对话、由它管十个 bot；销售工程讲者一周要为 15 到 20 个客户做案例幻灯；SDR 讲者每天 50 条新线索、5 条优先，训练文案语气时“对近期获正面回复的邮件加权，因为三个月前有效的东西现在完全不同了”。外部客户样本只有一个：Potrero Hill 的 Icon Coffee 让 bot 接 POS 系统，指出几个月只卖几份的菜单品项后下架，创始人估算每天省一到两小时。

官方承认的短板：验证码、登录态丢失、计算机使用慢于 API、跨账号互通不存在

问答里的坦白比演示更有信息量。销售工程场承认“我不是机器人”验证码当天已经出现几次，“有时过不去”，企业建议直接屏蔽 Facebook 等站点；Day 2 早些时候“有一次故障”；演示中 bot 登录 Google Slides 卡住需人工代登；Karen Cheng 的首要功能请求是“把登录管好”，虚拟机上的账号总被登出。Shub 承认“比 API 更快这个承诺有点难”，团队在做 headless（直接点 DOM 元素，跳过截图、判断、再点的循环）与模型加速。功能层面尚不存在的有：跨账号 bot 互通“今天不在我们能力范围内”；人类进入 bot 频道协作（Peter Yang 问“你们为什么还要用 Slack”）；API key 仍需手工创建；企业多人协同被两次问到，收入运营讲者说“有东西我不能抢先宣布，但很快会有”；Grok Bot 何时上 Tesla，两次回答都是“我不能回答”。营销场还澄清 OpenClaw 与 Grok Bot“并非原生互通”，但提供导入模板。

72 小时实验本身：方向反转、约 274 个 PR、零收入、“没有直播就没人玩”

Day 1 定下的方向是“快闪活动平台加自己在旧金山办一场”，当天收尾时 Lauren 已经在问“这是不是该追的问题”。Day 2 开场宣布转向，Roshan 的理由是“旧金山有很多限制与许可”、在直播上展示这类工作“不够有趣”，以及“我们让 agent 连夜跑了一遍，agent 告诉我们要转向”，改做游戏工作室，第一款游戏让观众把自己的 Grok Bot 模板铸造成卡牌互相对战。工程范式是极快且未经检验的：原型阶段 Lauren 决定删掉全部测试，“agent 总体上不太会写测试，等知道要测什么再写”；直推 main；Day 3 Matt 的反馈去重 bot“设成 YOLO 模式，直接合并”，与 Lauren 的 PR 撞车；Lauren 对隔夜自动合并的 PR 说“老实说我完全没看代码”。

Day 3 上线的 Thursday Arena 在收官时的数字（Vercel analytics，约中午开启）：约 1.7 万页面浏览、4500 练习局、近 2000 次 X 登录、练习到登录转化约 8%、近 5000 场对战、移动与桌面约五五开，流量主要来自 X 链接，每次回到直播就有一个流量小峰；团队三天用了“40、50、60 个 bot”，PR 编号到 274。Day 3 上午一位游戏设计评审 bot 的结论是“这游戏对上线来说太难了”，新注册在上午晚些时候开始放缓。变现停留在设想：体育场横幅广告位拍卖、“付费买排行榜置顶行”，最后一分钟以 1 美元竞价演示时“审核模块坏了”，Roshan 的收尾是“我们赚到了理论上的第一块赞助美元”，全程无真实收入，也没有留存数字。Lauren 的反思是“要不是在直播上，会有人玩这游戏吗？我觉得不会”，最难的是让人在意；Roshan 的收获是内部大公司用例出乎意料地能迁移到从零到一的小公司，“可以跑一套通用的生意剧本”，Eric 的总结是“先以人的身份去发现问题，解决之后再把它变成 bot 永远跑下去”。

外部嘉宾在 Day 1 给出的判断与主队的实际经历相互印证。Peter Yang 说“现在人人都能造东西，纯软件反而更难赚钱，我为什么要为一个带数据库的落地页付钱”；Codie Sanchez 说她的公司两年接入 1600 家小企业，为新书投放的“几百万美元”广告里企业感强的素材效果只有非企业感素材的四成，卖 AI 服务给小企业“绑不上即期收入就卖不动”，并明说自己的测评工具是用 Claude、Vercel 与 Replit 做的。Karen Cheng 的对照是自己此前用 Cursor 做硬件项目“像个冒牌货”，在 Grok Bot 里接 Vestaboard 只需贴 API key，“两分钟后显示屏开始翻页”。

对应用层的含义（作者归纳）

第一，模型厂自带的不再只是 harness，而是 harness、云端电脑、模板市场与 IDE 的整套垂直栈。本文之前精读过的 Zapier 的 Foster 主张应用层做“无头工具”接进用户的“日常主驾”，Grok Bot 的三天演示就是这个“主驾”的样子：编排层由平台自带，执行层由同一集团的 Cursor 承接，连接层靠计算机使用兜底。对靠“把模型接进企业工具”立身的应用商，这压缩的是集成本身的溢价，剩下的价值落在垂直知识、验证环境与合规责任上。

第二，单位经济的量级第一次从平台方口中给出。客服每张工单 1 到 2 美元、批处理 0.2 美元，与 Decagon 一类按解决量计费 1 到 10 美元的区间重叠，这意味着平台方的通用 bot 在简单工单上已具备价格压制能力，而讲者同时承认这来自“半天调优”、没有准确率与升级率数据，SDR 场对 token 花费的回避也说明用量计费下的成本仍不透明。三场 GTM 演讲把大量篇幅花在“怎么省 token”上，本身就是席位制向用量制迁移期的典型症状，与 Harvey 一期讨论的负毛利问题是同一件事的另一面。

第三，示范生意的含金量应打折。72 小时的产出依赖直播流量，转化约 8%，无收入无留存，团队自己承认没有直播就没人玩；真正有参考价值的是 xAI 员工的内部效率自述（两周落地、十小时构建、一个 bot 替代三四十个频道），以及验证码、登录态、故障这些反复出现的运行摩擦。把这两组信息放在一起看，Grok Bot 当前更接近“给已经 AI 化的旧金山公司用的内部工具”，Carrot 的 Eric 也说“可能先被我们这些很 AI 化的旧金山人采用，希望有一天所有中小企业主都用”。
