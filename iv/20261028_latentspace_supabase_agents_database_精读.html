当代理成为数据库用户：Paul Copplestone、Ant Wilson 谈 Supabase（Latent Space）

Latent Space · Paul Copplestone、Ant Wilson；主持人 swyx（Shawn Wang） · 2026-10-28 · 原始来源 ↗ · 中文精翻

关键词：编程代理；企业采用；用户增长；分发渠道；应用层护城河；Supabase；PostgreSQL

要点

  • Supabase 把长时计算放到数据库同一私有网络，并推进 OrioleDB、Multigres 和 Turso，分别应对性能、大型业务与海量数据库需求。
  • 两位创始人讨论声明式 schema、本地开发、代理推荐和企业销售，也复盘产品迁移与社区传播。主持人披露自己是早期投资者，Supabase 同时赞助节目。

00:00 主持人导言：为什么代理偏爱 Supabase

swyx： 又是我。希望大家喜欢最近这些节目前导，它让我有机会解释，为什么要做这一期，以及访谈中有哪些值得留意的内容，帮助你从访谈中得到更多。视频里也增加了叠加说明，既让画面更丰富，也解释一些新入行的听众可能不知道的概念，因为访谈时没时间逐一展开。

我最近去了 Supabase 的公司大会 Supabase Select，有很多内容值得聊。首先要说明，我与这家公司关系很密切。六年前，我参与了它的种子轮天使投资，它也是我的第一笔天使投资。过去六年，它的估值从零走到 100 亿美元。这是一家完全远程、开源的公司，如今几乎成为托管 Postgres 的标准选择。我想了解，它究竟为什么能做成这些事。

我也想了解，它为什么在我做的 AEO，也就是面向 AI 回答的推荐排名中表现那么好。这不是理所当然的，很多公司都在争夺“面向代理的数据库”这个位置。

它还是 2023 年第一届 AI Engineer 大会的第一家赞助商，我记得是这样。现在我们开放 Latent Space 赞助，它又将成为第一家赞助商。对于这件事，和我熟悉、信任，也能向听众解释清楚的公司及团队合作，是很自然的选择。

Supabase 的 YouTube 上有大会回顾，做得很好。这次大会有三条主线：构建、运营和扩展。发布内容很符合我对一家公司的大会主题演讲的期待。

“构建”主要是改善编程代理配置和使用 Postgres 的体验。有两项特别引起我注意。第一项很简单：不用 Docker 就能启动 Supabase。要启动基本进程、与数据库交互，依赖越轻越好。以后当然可以升级到完整虚拟机，但起步时不必那么重。

第二项是 Supabase Compute，把计算放在数据库旁边。这种就近部署很方便，我觉得被严重低估了，甚至他们自己也可能低估了潜力。

让你的应用通过 Supabase 客户端库获得 MCP 服务器也很好。还有声明式 schema，这特别重要。传统 SQL 的思路是，先建 schema，再迁移、迁移、不断迁移。我们在节目里会讨论这个问题。

如果希望 Git 成为唯一真实来源，让代理可以遍历、理解、设置和分叉整个系统，就需要另一种方式。听起来很简单，但 Postgres 当初不是为这个设计的，需要在一个已有四十年历史的数据库上补上这些能力。

我觉得 Supabase 现在的势头，在于补齐 Postgres 面向代理开发的最后一段路，把边界往前推，让代理真正好用。更妙的是，这些改进并不只是为了代理，人类本来就需要它们。我很喜欢这一点，不喜欢只为取悦代理而做事情。

第二条主线是“运营”，基本上是提供更多上下文：更多日志、检查、连接，为 SQL 提供 Markdown 文件，这很酷，还有知识和技能。他们每年也会发布有意思的数据管道，从 Stripe 到其他系统的集成。

随着 AI 工程经验增长，你会越来越多地接触 ETL，这本来属于数据工程体系。现在 Supabase 有了自己的原生方案，当然也可以和其他产品混合使用，但有时把东西放在一个地方确实方便。

最后一条是“扩展”，可能最复杂，也最关乎大规模业务。这也是 Supabase 把品牌表述改为“从原型到 PB 级”的原因。客户在成长，他们自然要支持更大的规模。

他们发布了 Multigres 的完整 v1，可以理解为面向 Postgres 的 Vitess 路线，而且是请到 Vitess 的原作者来做，这在数据库领域是一件大事。如果你不知道 Vitess，值得去了解：你正在用来观看这个视频的 YouTube，就由它支撑。

OrioleDB 等也有很多内容可聊。你会在访谈里看到我与两位创始人的关系。这应该是他们第一次一起接受播客访谈，我也会提到这一点，希望通过他们之间的互动，让你看到经营一家估值 100 亿美元的数据库公司是什么样。请听访谈。

05:23 两位创始人到访

swyx： 这期播客酝酿了六年。[笑] 很高兴请到 Paul 和 Ant，欢迎。

嘉宾： 谢谢邀请。

swyx： 我们在 Supabase Select 举行前录制，会在大会后发布。我想先庆祝一下你们一路走来的成绩。我从你们刚结束 YC 时就认识你们，那时你们在新加坡一个地方庆祝，我第一次见你们时还在想，这家热门数据库公司是怎么回事，好像是某个用户随手发到 Hacker News，就这样低调上线了。

恭喜你们取得今天的成绩。Select 这次有哪些主要发布？我们直接进入主题。

嘉宾： 发布内容很多。第一项是计算。我们现在有 Edge Functions，由 Deno 驱动，但存在两秒 CPU 执行时间的限制。社区很早就反复告诉我们，他们需要运行更长的工作负载。

06:39 把计算放在数据库旁边

嘉宾： 比如分块、生成嵌入等任务。明天我们会发布 Supabase Compute，等节目播出时大家已经能看到。它能运行各类程序，支持长时间任务，是无服务器的，并且和数据库处在同一个私有网络中。由于就近部署，延迟很好，可以直接从计算实例建立 Postgres 连接。

它不再局限于 Deno，可以使用 Rust 或 Python，也可以运行代理。基本上就是一个完整的计算实例。

swyx： 如果用大家熟悉的其他云产品来类比，它相当于什么？

嘉宾： 有点像 Lambda 函数，不过是支持容器的那种 Lambda。

swyx： 也就是说，可以运行完整容器。

嘉宾： 对。除此之外，我们在数据库方面有三项创新，分别针对性能、向上扩展和向外扩展。

第一项是去年谈过的 OrioleDB。过去一年，我们对它进行了非常严苛的测试，确保足够稳固，适合 Postgres 生态。它主要解决性能问题，是现有 Postgres heap 存储引擎的直接替代品。速度大约是原来的 1.5 至 2 倍，其他东西不需要改变。

08:05 OrioleDB 与 Multigres

嘉宾： 它完全兼容，还消除了对 VACUUM 等一些后台任务的需求，因此数据库运行也更高效。

过去一年，我们用 pg_regress 检查完整兼容性，做 Antithesis 测试，每晚跑 TPC-C 基准，并进行 Jepsen 测试，尽可能确保不会丢失数据。明天它会进入完整 beta 阶段，同时改为 Apache 2.0 许可。

这项技术带有专利，而 Apache 2.0 许可覆盖了相应专利授权。也就是说，我们收购技术，继续研发，支付专利费用，然后免费开放给大家。

swyx： 你之前轻描淡写说了一件让我一直难以释怀的事：你们测试了每一种 operator，发现它们在某些情况下都会丢数据。

嘉宾： 那是第二项，也就是扩展能力。

swyx： Multigres。

嘉宾： 对。我们研究了 Postgres 生态里的各种 operator。给不了解的人解释一下：运行 Postgres，最初通常是单节点，但几乎任何数据库最终都需要多个节点，还需要故障转移、备份管理等。这时通常会用一个 operator，帮助管理整个集群。

Postgres 生态有不少 operator，我们发现，在特定条件下，每一种都可能丢数据。因此 Multigres 从头重写了整个 operator 架构。

最初我们想为 Postgres 社区提供分片，但最后做出来的，更像一整套运行管理系统。我们进行了非常严格的测试，连续做了一千次故障转移，没有丢失任何数据，也用各种能想到的方式冲击它，观察是否会丢数据。现在对稳定性很有信心，明天也会发布。

它完全开源。在 Supabase 平台上，我们会先邀请部分客户使用。运行重要、大规模业务的客户可以来找我们，我们会协助他们扩展。

swyx： 这意味着 Multigres 已经完全达到与 Vitess 对应的能力，还是仍有未完成的部分？

嘉宾： 还没有。Sugu 当年为 MySQL 生态创建 Vitess，重点是分片。但他加入后说，这次最重要的是先解决兼容性。

过去使用 Vitess 分片时，经常需要改变一些查询，兼容性总是在追赶。所以他说，这次先把注意力完全放在兼容性上。

我们从头设计架构，就是为了将来发布分片时，你的数据库不需要任何修改，原有查询继续运行，Multigres 自动处理，应用代码零改动。

swyx： 这个愿景太棒了，而且你们两年就做到了。

嘉宾： 是一年。不过分片还没有发布。我已经看过早期原型和设计，其中一部分应该会在明年初落地，具体取决于平台其他工作的进展。我们同时在做很多事，但对方向很有信心，也很满意目前的进度。

swyx： 我觉得这是 Postgres 全面占据市场的最后一块拼图。不了解的人可以查查 Vitess，它支撑 YouTube，还支撑什么？

嘉宾： GitHub，还有很多服务。

swyx： 如果工作负载要从 MySQL 转向 Postgres，就需要这样的能力，Supabase 也才能赢。

嘉宾： 希望受益的不只是 Supabase 客户。这是完全开源的社区项目，任何大规模运行 Postgres 的人都应该能够使用 Multigres。

swyx： 想必整个 Postgres 生态的公司都会参与，因为大家都需要它。

嘉宾： 我们有设计合作伙伴计划，正在与 Booz Allen、Postman、Perplexity 等合作。很多客户加入，因为他们大规模运行 Postgres，确实需要帮助扩展的工具。

swyx： 第三项呢？

嘉宾： 第三项是向外扩展，也很重要。目前平台每个月会启动约五百万个数据库。

12:50 向上扩展、向外扩展与 Turso

嘉宾： 看未来的方向，我们觉得每个月可能需要启动数十亿个数据库。向外扩展是完全不同的问题，因此必须研究新的架构，以及代理数据库领域的人才。

在为代理服务这方面，Turso 是非常突出的数据库供应商。因此我们明天会宣布收购 Turso；等节目播出时，大家已经知道了。它会帮助我们构建面向代理的数据库。

swyx： 很了不起。它主要基于 SQLite，不过这里更重要的是架构，对吧？我不太确定该用什么词，广播式扩展？他们扩展 SQLite 的思路，是单个写入者和多个读取者吗？

嘉宾： SQLite 本身只能有一个写入者，而且是一种文件格式。所以一般来说……

swyx： 他们称之为给 SQLite 增加 MVCC。

嘉宾： 对。Turso 的架构为 SQLite 构建了多版本并发控制，让它可以有多个写入者。

swyx： SQLite 的许可有些特别，所以他们做了分叉。

嘉宾： 对，最初是 libSQL，后来又设计了一种很有意思的新架构。几周前，大家也大量讨论了把 WAL，也就是预写日志，放在 S3 上。

数据库领域的一些创新，实际上来自对象存储的进展。对象存储增加了很多新功能，让它可以有点像数据库一样使用。它的数据持久性大概有“十一个九”，不是可用性，二者不同。

swyx： 对，不是服务可用性，但它能提供通常需要数据库集群来实现的那些底层保障。

嘉宾： 就像下面已经有了一个集群。因此可以做很多有意思的事情，现在不少数据库和数据应用直接建立在对象存储之上。

在我们看来，它也有限制，可能更适合较小的使用场景。事务型数据库需要大量读写，所以特别大规模的事务负载，大概不该用这种方式，这也是我们为什么要做 Multigres。

但要达到数十亿个数据库的规模，我们需要数据库能够以文件形式存在。SQLite 在这方面非常有吸引力，已经占据很重要的位置。

真正引起我们兴趣的是 Glauber 发的一篇文章，介绍他们的重写工作。我联系他，因为那套架构让我们看到，在他们的文件格式上实现 Postgres 兼容性的路径。

收购后我们会保留 Turso 品牌，让它继续专注 SQLite。Supabase 则会推出一种更小的实例类型，叫 Supabase Spark，与我们所有客户端库兼容。任何一个想法、任何一个原型，都能有自己的数据库。业务发展起来后，再升级到完整的 Postgres，最终一路扩展到 Multigres。

swyx： 我知道你们为此努力很久了，这就是梦想中的状态，对吧？

嘉宾： 对。向上扩展和向下缩小，一直都是我们想解决的问题。直到这些创新出现，我们才意识到，现在终于可以做到了。

swyx： 从每月五百万个数据库走向数十亿，其中一个关键是，它们其实都很小。很多是用自然语言编程做出来的小应用。你们观察到什么？

嘉宾： 在它们获得用户之前，确实很小。但如果突然上了 Hacker News 首页，就需要知道自己还能继续扩展。

因此整套设计必须提供顺滑的后端迁移路径，零停机迁移是必需的。现在很多非技术背景的人，已经在构建完整的公司。我们的客户 MagicSchool，创始人原本是一名教师，看到老师花太多时间做本可以自动化的工作，就开始创业。

没有技术联合创始人、没有 CTO 的创业公司，已经不是孤立案例，而是越来越常见。

嘉宾： 每个人都在变成构建者。这也是过去 18 个月增长如此惊人的原因。但我觉得仍然很早期，未来会有更广泛、几乎像普通消费者一样的构建者：企业内部的人，或者想创办自己公司的人，都会需要数据库。

17:53 开发者营销与梗图

嘉宾： 如果给每个人都配置一个专用 Postgres 集群，我们很快就会用完世界上的物理计算机。[笑] 基本上，我们现在就在面对这个问题。

嘉宾： 对，今年一直在应对增长带来的计算容量压力。

swyx： 恭喜。另外我感觉，Glauber 也是个梗图高手。

嘉宾： 对，这也是重要原因之一。他很厉害。

swyx： 不知道的人可能没意识到，Supabase 那些梗图背后的就是眼前这位，平时不声不响，其实很厉害。

嘉宾： Ant 和 Glauber 都是。

swyx： 你们会交流什么东西好笑吗？

Ant： 我们肯定会给他 Supabase 的 Twitter 账号权限，我也需要帮手。

swyx： 等等，现在还是你在负责？

Ant： 现在有个小团队帮我，一群年轻人。[笑] 我们每周做一次梗图工作坊。不过这类岗位很难招，因为既要理解技术，也要知道开发者觉得什么好笑，才能做好这种营销。

嘉宾： 你其实也是个隐藏的梗图高手。

swyx： 我没你那么好笑。你真的很厉害。之前有一张海鸥的图，是 Supabase 站在 Postgres 上面，像一只海鸥骑在另一只飞行的海鸥身上。我现在找不到，但这属于 Supabase 的老历史了。

当时那些内容好得让别人想模仿，却模仿不了，梗图简直成了你们的护城河。

Ant： 有一些非常大的公司也试图在官方 Twitter 上发梗图，我就不点名了。但这很难，相关人才也很难招。

嘉宾： 有个人还写了一篇大概四万字的长文，分析我们的梗图策略。

嘉宾： 很早就有人研究我们的 Twitter 策略，发到 Hacker News。好笑的是，他把我们自己还没写下来的策略总结出来了。后来新营销同事加入，我们就说：“这是我们的策略，只不过是别人写的。”[笑]

swyx： Hacker News 当然又骂了这篇文章，然后评论……是这个人写的吧？《观察 Supabase 动态四个月的收获》。他就是在研究你们的工作。什么时候的？2022 年。等等，我也提过这篇，哦，我在这里。

嘉宾： 他做了分析，Hacker News 批评它，然后 Ant 把那些批评截图，发到了我们自己的 Twitter 上。

swyx： 你们的讨厌只会给我动力。[笑] 我当时还评论说“有意思的文章”。

嘉宾： 早期增长很大一部分来自 Hacker News。那时候我几乎得整天泡在上面。

swyx： 那必须聊聊了。你们和管理员 dang 做了什么魔鬼交易？

41:43 产品驱动销售与企业增长

嘉宾： 我们几乎把所有注意力都放在成为一家“指数型公司”上，也就是让自己随整个客户群成长。榜样是 Stripe。在我们见过的开发工具公司里，它是少数在十多年持续进入更大客户市场的同时，还能保有开发者喜爱的公司。

因此开始做销售时，我们只是叠加了一层“产品驱动销售”。我们观察产品触发信号：可能是一个很重要的客户标志，但更重要的是，客户正在扩大规模、碰到限制、出现错误，或者付费达到某个水平。

后来 AI 出现，我们发现可以做很多有意思的事。假设每周出现一千个产品触发事件，我们向遇到问题的用户发一千封邮件，有五百人回复。没有回复的那一组，被我们当作对照，观察其增长，发现他们的账户每月增长约 25%。

对于回复的人，我们给销售团队的任务只有一个：与他们通话，帮助解决问题。因为我们掌握流量模式，知道他们遇到什么，可以利用 AI 给销售准备谈话提纲。这方面 AI 很有用。

结果发现，只是通话并提供帮助，这批账户就会增长 125%。两组之间额外的 100 个百分点，就是我们给销售计算报酬的依据。

传统做法是让销售去卖产品，然后把全部业绩算到销售头上。但我们知道，这类用户即使没有销售介入，平台消费也会自然增长 25%；因此要识别销售额外带来的那部分增长。我们的销售一直围绕重要客户，或者非常具体的产品需求。

企业客户通常因为需要启动很多数据库而进来，几乎不会是把现有生产数据库迁过来。从 MySQL 迁到 Postgres，或者从一个可扩展数据库迁到另一个，几乎不发生。

这也是 Supabase 最初的核心判断。我们研究过那些试图靠迁移增长的 Postgres 公司和数据库公司，发现这条路长期很难成功。即使你的 Postgres 更大、更好、更能扩展，也很难说服别人迁移。

你必须在第一天就获得客户，再让他们留到第一千天、第一万天。因此我们的重点，是在企业新项目的第一天进入。

嘉宾： 对，新建项目。

嘉宾： 我敢说，他们几乎不会迁移。有一批客户确实需要 Multigres，我们与一些想用开源版本的企业讨论过。他们正在遇到大规模 Postgres 的问题，希望参与影响产品方向。

49:38 在线迁移、分析系统与下一阶段增长

嘉宾： 在数据分析领域，从一个数据仓库迁到另一个，通常比较容易。问题是，OLTP，也就是在线事务处理数据库，往往支撑着最能产生收入的应用。停机一分钟，就意味着真金白银的损失。

因此通常得让新旧两套系统并行运行，接着又面临“脑裂”风险：一部分数据在这边，另一部分在那边。任何尝试过对账和重新统一两边状态的人都知道，这非常难。

OLTP 的风险高得多，所以大家往往选择拆分工作负载：新业务放到新系统，逐步迁一些操作，期待慢慢完成迁移。

swyx： 但通常你就变成有两个问题了。[笑]

嘉宾： 是吗？

swyx： 对，就是数据库领域那条一直追逐的白鲸。传统上，你需要一个 OLTP 数据库和一个 OLAP 分析数据库，两者分开，但有时又希望不必复制任何数据。你们关注这件事吗？Supabase 将来会有相关方案吗？

嘉宾： 关注，我们特别感兴趣的是 DuckLake。DuckLake 和 DuckDB 都是很有意思的技术。

swyx： 是 MotherDuck 再加一个数据湖？DuckLake 到底是什么？

嘉宾： DuckDB 可以理解为分析领域的 SQLite。

swyx： 列式存储。

嘉宾： 对。它能直接读取对象存储，这也是最常见的宣传方式，还能读取 Postgres 数据库。它是很棒的开源技术。DuckDB Labs 最近被 AWS 收购了，相关基金会也在构建围绕开源项目的治理委员会。

我有点把 DuckDB 看作分析生态里的 Postgres：努力让它不属于任何一家企业，功能多、适用面广。

swyx： 最初是荷兰的教授做的。

嘉宾： 对，他们生活和工作都在荷兰，很有意思。

所以我们认为，要扩展到 PB 级，分片是更好的办法，而分析业务应单独处理。这不意味着不能把数据直接存到对象存储，再从另一条路径读取，只是硬把两种用途揉在一起，在我看来未必合理。

swyx： 我们可以先聊到这里，因为还有很多内容。他们的一些创新，据我理解，是利用数据库机器上的空闲计算能力来做复制。

嘉宾： 坦白说，我没有深入研究他们具体怎样实现 HTAP，也可能理解不准确。

swyx： 对，你们有自己的方向，客户也没有敲桌子要求这个。但如果想成为领先的数据库公司，总有一天得有答案。

58:43 面向代理的本地开发与团队协作

嘉宾： 今年重点是走向代码优先、Git 原生。在本机启动 Supabase 实例后，会得到一个 Supabase 文件夹，它代表你的数据库，包含函数等所有内容。

swyx： 这个今天已经有了吗？

嘉宾： 用我们的 CLI 就有。

swyx： 像一个虚拟文件系统？

嘉宾： 更像基础设施即代码，用文件表达整个系统。

明天我们会发布声明式 schema 的一项最终改进。覆盖整个 Postgres 非常困难，但现在可以在文件夹里用完整的文件形式，声明数据库应该是什么样。

这对代理很重要。通常使用 Postgres，每次变更都新增一个迁移文件，形成历史日志，这是行业标准。但如果把一千个文件交给代理，问某张表现在是什么结构，它就得从一千次变更里推导。

swyx： 相当于重新编译一遍历史。

嘉宾： 或者在本地启动数据库，执行全部迁移，再查询数据库结构，但这太慢。

我们想把 Supabase 目录里的 schemas 文件夹，变成数据库当前状态的完整声明。表、策略、数据库注释，都放在文件中。为此会发布新库 pg-delta，可以用于任何 Postgres 数据库，同时我们也提供与 Supabase 配合的机制。

代理主要操作代码，不想反复访问外部系统，需要在文件系统里快速迭代。今天大家使用 CLI，也接受当前的代理运行框架，但我怀疑未来会继续变化。

比如我现在尝试只用手机开发，已经相当顺畅。当然，我了解背后发生什么，所以会从基础设施角度告诉代理该做哪些事。

但我能想象，未来不需要工程师背景。你有个想法，对手机、随身设备或者个人代理说“我想做 X”，一秒后就有一个上线的应用，然后自己继续迭代。

因此我在想：人们会需要什么应用，会不会是高度个人化的？这些东西会不会做大？开发机制怎样变化？我们需要提供什么工具，才能成为这个新世界的默认供应商？

swyx： 另一位有什么想让水晶球回答的问题？

嘉宾： 做了几十年软件工程，我对软件应该怎样构建有很强的看法，比如持续集成、持续交付。现在我经常把自己的意见强加给代理：“你应该这样做。”但越来越发现，也许并不需要。

我担心的是，最后所有代理会不会都收敛到同一种软件开发方式？

swyx： 模式坍缩。

嘉宾： 对。当然，如果所有人都用 Supabase，对我们很好。[笑] 但软件行业很棒的一点，是大家会为正确做法激烈争论，甚至出现著名的口水战。我们会失去这种东西吗？

swyx： 你希望观点保持多样，让最好的想法胜出。但模型可能让人越来越懒，没人再看细节。

嘉宾： 对，最后全都用同一种方式开发，会不会停在局部最优？

嘉宾： 确实。[笑]

嘉宾： 好问题。我们合作有效的原因之一，是虽然会有分歧，但只要一方稍微坚持一下，另一方通常就会说：“也许你是对的，我们试试。”

1:06:43 开源社区、AI 开支与公司工作流

swyx： 你们为社区和开源做了很多。我一直在想，大型商业开源公司的未来是什么？一方面，AI 生成的低质量内容很多，你们肯定也在应对。另一方面，软件依赖似乎变得可有可无，因为现在想要什么，都可以让代理重新写一个。你们怎么看？

嘉宾： 用 Rust 重写，是一种合理路径。我们团队有人对我说：“我要把我们做的一切都用 Rust 重写。”我问：“重写到哪一层？数据库也重写？Postgres 也重写？”

Postgres 不是 Rust 写的，但我怀疑你会在意到那个层次。你总会在某个层级停下来，不会把所有创新精力，或者所有 token，都花在重写一切上。

所以可能很多工具会收敛到某种语言，比如 Rust，如果它最终因为更快、更正确而成为最好的方式。很多开源工具可能会经历这样一轮变化。

但等这一轮完成，大家都跑在高效语言上，就不会每次都重写所有东西，最终会有少数胜出者。

PostgREST 就是个典型例子。它用 Haskell 编写，这门语言不常见，维护比较难。现在能用 Rust 重写吗？大概可以。但它提供的机制和功能仍有价值。如果真的发生，可能会有一个 Rust 版 PostgREST 分支，成为这个品类的赢家。

swyx： 但你们还没这么做，而且你们不少东西是 Elixir 写的。

嘉宾： 对，这时还要考虑基础设施运行。Elixir 因为 BEAM 虚拟机而非常有意思。运营系统时，什么机制最合适，也是另一个问题。

swyx： 现在只要能通过测试，切换开发范式也容易得多。

嘉宾： 是的。我还真没认真想过，要不要把 Elixir 换成 Rust。

swyx： 至少现在这是一个选项。Vercel 的 Malte 有条推文让我印象很深：拿出一笔钱，把我们所有 C 或 C++ 层的依赖重写成 Rust，因为知道它在安全性、正确性等方面更好。

这就像给开源生态做一次升级，包括所有驱动和其他依赖。我觉得很有意思。

嘉宾： 我很喜欢这个主意。不过它可能未必会发生，因为大家喜欢各自重做一遍。但作为一个想法，我们公司绝对愿意支持。

swyx： 最后一个问题，本来应该早点问。你们显然受益于外部的编程代理，那 Supabase 内部呢？AI 编程政策是什么，花多少钱，会担心成本吗？

嘉宾： Supabase 一直像很多不同的创业公司拼在一起。比如认证产品团队，我们一直坚持让他们自己决定工具、工作方式、团队行为和汇报结构。

AI 政策也是一样。很多人问公司统一的 AI 编程政策是什么，我们说，由各团队自己决定。现在开始在一些地方做整合，特别是成本，但只要可能，仍然希望团队自己决定怎样运行。就是这么分散。[笑]
